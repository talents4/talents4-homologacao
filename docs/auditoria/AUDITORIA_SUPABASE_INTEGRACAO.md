### `07_auditoria_tabelas_desconhecidas.sql`: as 3 tabelas "fantasmas" são, na verdade, **um sistema paralelo inteiro**

Este é o achado mais importante da auditoria. As 3 tabelas não são acidentes isolados — são parte de **duas famílias de tabelas que existem no mesmo projeto Supabase e não têm nenhuma relação com o código deste repositório**:

**1) Uma geração anterior (ou paralela) do próprio CRM organizacional**, prefixo `org_`: `org_matches` (15 linhas), `org_employer_profiles` (7 linhas), e — descobertas pelas chaves estrangeiras que apareceram no resultado, não pela sondagem original — `org_openings`, `org_meetings`, `org_notes`, `org_documents`, `org_activities`, `org_pipeline_items` (essas 6 eu ainda não consultei diretamente; sei que existem porque `org_matches` tem FK para `org_openings` e 5 tabelas diferentes têm FK apontando **para dentro de** `org_matches`). A forma de `org_matches` (candidate_id + opening_id + employer_id + status + priority + score + next_action) é estruturalmente quase idêntica ao papel que `talent_opportunity_matches` cumpre hoje ("Seleções modernas", no meu próprio relatório de auditoria de código) — e `org_employer_profiles` (focus_areas, company_summary, drive_folder_link, color_tag, notes) sobrepõe parcialmente o que hoje é calculado no cliente (`window.T4Modern.color()`) ou vive em `employers.descricao_*`. **Hipótese, não fato confirmado: isto é o schema de uma versão anterior do Organizacional, substituída pela geração atual, e nunca removida.** As policies usam a mesma função `can_edit_crm()` que o resto do app usa — ou seja, foi construído pela mesma equipe/ferramenta, não é uma ferramenta de terceiros.
- **Achado de segurança pontual:** `org_matches` tem GRANT de tabela para o papel `anon` (SELECT/INSERT/UPDATE/DELETE) — mas as 4 policies de RLS listam só `roles=authenticated`, então, na prática, `anon` não consegue ler nem escrever nenhuma linha (RLS nega por padrão quando nenhuma policy lista o papel que está conectado). **Não é uma brecha ativa**, mas é uma inconsistência com o padrão mais estrito usado no resto do banco (grant só para quem a policy realmente autoriza) — mesmo tipo de achado "defesa em profundidade" já registrado na auditoria da primeira fase desta conversa. Correção sugerida (não aplicada): `revoke all on org_matches from anon;` — comando reversível, de impacto zero no funcionamento atual (RLS já bloqueia o acesso mesmo com o grant).

**2) Um pipeline de importação de candidatos via Google Drive**, tabelas `drive_import_drafts` (0 linhas hoje), `drive_nodes`, `drive_connections` (essas duas só conhecidas pelas FKs de `drive_import_drafts`, ainda não consultadas diretamente). `drive_import_drafts` tem: status de revisão, detecção de duplicidade (`duplicate_candidate_ids`), sinalizadores de atenção (`attention_flags`), campos faltantes (`missing_fields`), origem/versão do "parser", e FK direta para `candidatos` (tanto `proposed_candidate_id` quanto `created_candidate_id`). Tem gatilhos ativos (`validate_drive_import_source`, `touch_drive_updated_at`) — não é scaffolding abandonado, é algo com validação de verdade. **O papel `authenticated` só tem `SELECT` nessa tabela — quem escreve nela é `service_role` ou `postgres`, ou seja, algum processo de backend (Edge Function, automação externa, script com a chave de serviço) fora deste repositório.** Isto bate com a hipótese natural do nome: uma automação que lê uma pasta do Google Drive, tenta casar cada arquivo com um Talento (candidato) já existente ou propõe um novo, e grava um rascunho aqui para revisão humana — mas **isto é inferência a partir da estrutura, não confirmação**.
